Introduction

Vous allez écrire à peu près la même application Web que dans le TP 1, un chat avec un LLM, mais en utilisant LangChain4j pour accéder à l'API du LLM (Gemini).

Dans le TP 1 vous avez écrit une application qui utilisait directement les endpoints REST de l'API du LLM, avec des documents JSON explicitement construits dans l'application. LangChain4j permet de travailler à un plus haut niveau, sans s'occuper de la manipulation des documents JSON, qui est assez pénible et, surtout, qui est différente pour chaque LM.

LangChain4j

Le framework LangChain4j est actuellement un standard de facto pour l'utilisation des LLM en Java, et en particulier pour faire du RAG. Il permet un plus haut niveau d'abstraction.

LangChain4j est au départ une adaptation à Java de LangChain mais aujourd'hui les 2 projets ont évolué indépendamment et suivent des trajectoires distinctes. LangChain4j est un framework open source qui ajoute une couche d'abstraction aux APIs des LMs. Cette couche d'abstraction améliore la portabilité des applications (il est ainsi plus simple de changer de LM ou de base de données vectorielle, par exemple) et facilite l'utilisation des APIs. LangChain4j permet d'enchainer aisément plusieurs interactions avec des LMs, et des traitements complémentaires ; par exemple

  • Lecture de fichiers ou d'une base de données pour les faire prendre en compte par les LMs.
  • Accès Web pour vérifier une information donnée par un LM.
  • Cadre pour écrire des applications multi-agents.

Dépendance Maven à ajouter pour LangChain4j aux fichiers pom.xml de vos projets Java (choisissez le dernier numéro de version, à la place de 1.22.0 ; le numéro doit être le même pour toutes les dépendances liées à LangChain4j) : 

<dependency>
   <groupId>dev.langchain4j</groupId>
   <artifactId>langchain4j</artifactId>
   <version>1.22.0</version>
</dependency>

Dépendance Maven à ajouter en plus pour l'utilisation de l'API de Gemini avec LangChain4j :

<dependency>
   <groupId>dev.langchain4j</groupId>
   <artifactId>langchain4j-google-genai</artifactId>
   <version>1.22.0-beta32</version>
</dependency>

Test 4 : Embeddings

Classe Test4Embeddings.

Le programme que vous allez écrire utilise un modèle d'embeddings pour calculer la similarité de 2 phrases par la métrique du cosinus appliquée à leurs embeddings.

LangChain4j a des modèles d'embeddings intégrés et qui ne coûtent rien en tokens, mais ils ont été entrainés avec des textes en anglais et les scores de similarités fournis peuvent être vraiment mauvais sur des textes en français. Pour cet exercice commencez à en utiliser un (BgeSmallEnV15EmbeddingModel, utilisé par EasyRAG, vu dans l'exercice suivant) pour éviter de rogner sur votre quota. A la fin de l'exercice, passez à un modèle d'embeddings plus performant. Si vous ne l'avez pas déjà lue, lisez cette page qui donne quelques conseils pour économiser les coûts en tokens.

Donnez au moins 6 couples de phrases pour voir la similarité. Par exemple le premier couple contient 2 phrases similaires et le deuxième 2 phrases opposées. La valeur de similarité en elle-même n'est pas ce qui importe le plus. Il est surtout important que des phrases similaires aient une valeur de similarité supérieure à des phrases non similaires. En effet, cette valeur de similarité sera utilisée par le RAG pour choisir, par exemple, les 5 documents les plus similaires à une question parmi tous les documents enregistrés.

Pour récupérer les embeddings à partir des réponses du modèle d'embeddings, utilisez la méthode content().

Pour calculer la similarité, utilisez la classe CosineSimilarity (cherchez dans la javadoc ou le support de cours). En théorie, les valeurs retournées par la méthode between vont de -1 à 1 mais, avec les modèles d'embedding les plus utilisés, elles sont le plus plutôt comprises entre 0,5 à 1. Remarque : la plage des valeurs pour la similarité n'est pas importante. Par exemple, dans le cas du RAG (voir les questions suivantes), si l’on compare un texte T à une liste de textes, on souhaite que les n textes ayant la plus forte similarité avec T soient ceux dont le sens est le plus proche de T et la plage des valeurs n'est pas significative.

Quand le code vous semble correct, utilisez un modèle d'embedding externe fourni par Google (une classe Java fournie pas LangChain4j facilite son utilisation et votre clé Gemini peut être utilisée) qui se comporte mieux avec des phrases en français, et en d'autres langues. Laissez l'ancien code en commentaire ou, mieux, gardez les 2 modèles d'embeddings pour comparer leurs résultats sur les 5 phrases.

Une des difficultés est de trouver le bon nom de modèle pour les embeddings. La liste des noms de modèles externe de Google peut être obtenue en tapant cet URL dans un navigateur :
https://generativelanguage.googleapis.com/v1beta/models?key=AIzuuyDTjkuPHjBY... (collez ici votre clé Gemini). Attention, le nom du modèle à mettre dans le code est le nom qui est après "models/" dans la liste des modèles. Utilisez par exemple le nom de modèle "gemini-embedding-001".

Optionnel (les parties optionnelles du cours et des TPs vous permettent d'en savoir un peu plus ; vous pouvez les ignorer si vous êtes à court de temps) : Cette page pourra vous aider à faire le meilleur choix du modèle d'embeddings pour vos autres projets.

Pour écrire le code Java avec le modèle d'embedding de Google, allez voir l'interface EmbeddingModel et la classe GoogleGenAiEmbeddingModel dans la javadoc de LangChain4j. Utilisez le design pattern "builder" pour créer une instance de GoogleGenAiEmbeddingModel. Pour le type de tâche, choisissez TaskTypeEnum.SEMANTIC_SIMILARITY puisque vous voulez calculer une similarité. Pour la durée du timeout, utilisez la classe Duration du JDK ; essayez 100 ms et augmentez si ça ne suffit pas.

Copiez les couples de phrases et leur similarité dans l'email que vous allez envoyer. Si des résultats vous semblent curieux, ou si vous voyez des grosses différences de qualité entre le modèle intégré et le modèle externe, signalez-les.

Il se peut que les réponses à vos questions ne vous conviennent pas. Plusieurs raisons peuvent l'expliquer :

  • Le code qui vous a été fourni est très simple car il utilise des classes par défaut pour les embeddings, qui ne sont pas bien adaptées au français. Mais attention, si vous avez un compte gratuit, l'utilisation d'un modèle d'embedding externe comme celui de l'exercice sur les embeddings ci-dessus aurait pu provoquer une erreur de quota en une seule exécution (le modèle d'embeddings va calculer l'embedding de tous les segments, et vous êtes limité dans le nombre de requêtes par minute).
  • La phase d'ingestion (au début) utilise une configuration par défaut qui peut ne pas convenir, En particulier, le nombre de tokens de chaque segment peut ne pas convenir. Le TP 4 vous montrera comment modifier les valeurs par défaut.
  • Le fichier PDF "brut", sans aucune préparation, que vous avez utilisé est découpé en morceaux de tailles fixes par défaut. Cependant ce fichier contient plusieurs slides par page et le découpage a peu de chance de correspondre à un découpage efficace. Si vous êtes intéressé, vous verrez dans le TP 4 une partie optionnelle qui fait un meilleur découpage.

Conclusion :

Un LLM peut parfois se tromper, broder et même inventer des informations, c'est son péché mignon. C'est pour cela qu'il faut parfois lui mettre des garde-fous.

Les connaissances qu'il a acquises viennent de son entrainement durant lequel il n'a pu consulter les documents privés des entreprises, et elles datent de la fin de cet entrainement.

Le RAG permet de lui fournir des informations supplémentaires au moment de chaque question, sur lesquels il peut s'appuyer. Mais le RAG n'est pas infaillible ; le LLM peut encore ne pas donner la bonne information, avec le bonne façon de le dire. Il faut toujours faire de nombreux tests, avec intervention humaine, avant de mettre en production une application qui utilise une IA.

Une bonne préparation des documents sources utilisés par le RAG (ici le seul fichier PDF du support de cours) est aussi le plus souvent nécessaire ; vous en verrez un exemple dans le TP sur le RAG. Une bonne configuration du RAG est aussi nécessaire.

Evidemment, les RAGs réels ne se limitent pas à consulter un seul fichier. Vous verrez dans le cours sur le RAG que les embeddings créés à partir de multiples fichiers ou bases de données de l'entreprise, de types divers (texte, pdf, docx, image pour certains LLMs,...), peuvent être enregistrés dans une base de données vectorielle persistante (pas un entrepôt conservé dans la mémoire, comme pour cet exemple).

Test 7 : Utilisation d'outils

Classe Test7Outils.

Exécutez Test 2 en posant la question "Je dois partir dans 2 jours à Paris ; j'y resterai 3 jours. Est-ce que je dois mettre un parapluie dans mes valises ?". Est-ce que l'IA vous donne une réponse qui vous convient ? Vous copierez la question et la réponse dans l'email que vous allez envoyer pour ce TP.

Vous venez de voir comment récupérer des informations depuis des fichiers privés mais ça n'est pas suffisant pour répondre à certaines questions.

Des outils peuvent étendre les fonctionnalités d'un LLM. Un outil pourra, par exemple, faire des calculs mathématiques complexes, manipuler des bases de données, accéder au Web, gérer des emails, ce qu'un LLM ne peut pas faire de base. Les outils sont importants ; ils sont en particulier utilisés pour écrire des agents IA qui peuvent effectuer des tâches complexes. Les chatbots qui utilisent les LLMs (comme les applications ChatGPT, Gemini ou Claude Desktop) intègrent déjà des outils et permettent d'ajouter d'autres outils.

Pour ce test, vous allez permettre au LLM d'utiliser un outil pour avoir des prévisions météo. De base, un LLM n'a pas de connaissances en temps réel. Son savoir se limite aux informations présentes dans les données utilisées lors de son entrainement.

LangChain4j vous permet d'écrire l'outil en Java et de le rendre utilisable par le LLM facilement (voir cours).

L'outil va permettre au LLM de connaitre les prévisions météo pour les précipitations dans un lieu défini par sa latitude et sa longitude. Il sera basé sur l'API Open-Meteo qui est open-source, d'accès gratuit et ne nécessite pas de clé. Documentation de Open-Meteo : https://open-meteo.com/en/docs.

Paris a la latitude 48,85 et la longitude 2,35. Commencez par tester l'API en tapant directement cette URL dans votre navigateur : https://api.open-meteo.com/v1/forecast?latitude=48.85&longitude=2.35&daily=precipitation_probability_max&forecast_days=3. Vous allez obtenir les probabilités maximales d'avoir de la pluie pour les 3 jours à venir, jour courant compris, pour la ville de Paris sous la forme d'un document JSON de ce type (pourcentages de chance d'avoir de la pluie pour les 3 jours dans tableau "precipitation_probability_max") :

{
  "latitude": 48.853382,
  "longitude": 2.355208,
  "generationtime_ms": 0.0524520874023438,
  "utc_offset_seconds": 0,
  "timezone": "GMT",
  "timezone_abbreviation": "GMT",
  "elevation": 46,
  "daily_units": {
    "time": "iso8601",
    "precipitation_probability_max": "%"
  },
  "daily": {
    "time": [
      "2026-03-09",
      "2026-03-10",
      "2026-03-11"
    ],
    "precipitation_probability_max": [10, 13, 98]
  }
}

Le cours vous explique comment un LLM peut utiliser un outil (pas vraiment évident...). C'est bien plus simple en utilisant LangChain4j car il suffit d'écrire une méthode Java et de l'annoter par @Tool. Voici une classe MeteoTool. Le paramètre de @Tool doit être assez clair pour que le LLM sache s'il a besoin de l'outil pour répondre à une requête.

Commencez par tester cette classe en faisant afficher la météo d'une ville que vous choisissez. Ecrivez une classe TestMeteo qui utilise la méthode isPluiePrevue de la classe MeteoTool. Vous pouvez jouer sur la variable seuilPluie pour tester le bon fonctionnement de cette méthode.

Service IA

LangChain4j utilise la notion de "service IA". Cette notion facilite l'écriture pour les cas plus complexes en ce plaçant à un plus haut niveau d'abstraction que le code de base donné par LangChain4j. Elle peut aussi être utilisée pour les cas simples. Vous avez utilisé un service IA dans les tests sur le RAG ci-dessus.

Un service IA définit un comportement pour des échanges de messages entre l’application et le LLM.

Le développeur définit une interface Java qui contient les méthodes qui correspondent aux interactions que son application aura avec le LLM. Vous mettez dans cette interface les méthodes que vous voulez. LangChain4j fournira automatiquement une implémentation de cette interface avec un objet proxy (vous n'avez pas besoin d'implémenter l'interface). Les méthodes de l'interface seront des échanges de messages (questions et réponses) entre l’application et le LLM ; LangChain4j tient compte des types des paramètres, du type retour et des annotations des méthodes pour fournir l'implémentation de l'interface Java.

Pour ce projet l'interface sera très simple, avec une seule interaction qu'on appelera chat (on peut choisir le nom que l'on veut) : une question (prompt) est envoyée au LLM et il répond :

public interface Assistant {
  String chat(String prompt);
}

La classe AIServices de LangChain4j permet de créer une "instance de cette interface" (en fait c'est une instance de la classe "proxy" créée par LangChain4j, qui implémente l'interface). La classe LlmClient utilise cette instance pour envoyer des messages à l'API du LLM.

Créez cette interface dans le même package que la classe LlmClient.

Variables d'instance de LlmClient

  • String systemRole : le rôle que l'utilisateur choisira pour l'assistant IA.
  • Assistant assistant : Assistant est l'interface que vous avez défini pour décrire les interactions avec le LLM.
  • ChatMemory chatMemory : la mémoire utilisée par l'assistant pour garder l'historique de la conversation. En effet, l'API des LLMs est sans état et c'est au client de garder l'état de la conversation (tous les messages échangés depuis le début de la conversation). Dans le TP 1 vous passiez l'historique à chaque requête. Maintenant, c'est LangChain4j qui va s'en occuper pour vous. ChatMemory est une interface de LangChain4j qui facilite la gestion de l'historique de la conversation.

Constructeur de LlmClient

  1. Récupère la valeur de la clé secrète du LLM avec la méthode Java standard System.getenv.
  2. Crée une instance de type ChatModel qui représente le LLM. Pour la création du modèle, utilisez le builder pour passer la clé de l'API et donnez le nom du modèle (gemini-3.5-flash par exemple).
  3. Crée l'assistant en utilisant la classe AiServices fournie par LangChain4j. Remarquez la configuration de la mémoire pour garder jusqu'à 10 messages : 
    this.chatMemory = MessageWindowChatMemory.withMaxMessages(20);
this.assistant = AiServices.builder(Assistant.class)
                           .chatModel(model)
                           .chatMemory(chatMemory)
                           .build();

Remarque (pas demandé pour ce TP) : Si vous voulez permettre à l'utilisateur de modifier des paramètres du modèle, par exemple la température, il faudra reporter la création du modèle et de l'assistant au moment où la première question est posée. Il faudra alors garder l'assistant dans une variable d'instance pour ne pas le recréer à chaque nouvelle question.

Méthodes de LlmClient

2 méthodes :

  • Un setter pour le rôle système (celui indiqué par la liste déroulante de la page JSF). Il ajoute ce rôle à la mémoire, comme instance de type SystemMessage pour qu'il soit pris en compte par le LLM. Lorsque le rôle système est mis, le contexte change tout à fait et donc il vaut mieux vider la mémoire avant de mettre le rôle système. Dans le backing bean n'oubliez pas d'utiliser ce setter dans le cas où on est au début de la conversation. Attention, passer le rôle système ne suffit pas, il faut l'ajouter à la mémoire pour que le LLM en tienne compte.
  • Une méthode qui envoie une requête au LLM et qui reçoit une réponse en retour. Cette méthode utilise l'instance de l'interface Assistant (instance dont la classe est implémentée par LangChain4j comme c'est expliqué plus haut).

AVERTISSEMENT : Cet exercice est optionnel : vous n'êtes pas obligé de le faire. Il est assez long ; ne le faites que si vous avez de l'avance et que vous ne pouvez pas passer tout de suite au prochain TP.

Les LLMs affichent leurs réponses en streaming : ils n'attendent pas d'avoir généré tous les tokens de la réponse pour l'envoyer à l'utilisateur. Ils envoient les tokens de la réponse dès qu'ils les ont générés (en fait certains LLMs, comme Gemini, regroupent les tokens ; le streaming envoie alors des groupes de tokens et pas des tokens isolés). Vous allez faire de même.

Pour cela vous allez utiliser une option de LangChain4j qui permet d'obtenir la réponse token par token pour l'API du LLM.

Les échanges entre le serveur et la page JSF vont utiliser un websocket.Vous allez ajouter un websocket dans la page JSF de l'application qui fait l'interface avec l'utilisateur, en utilisant la balise JSF <f:websocket>. Cette balise va indiquer les fonctions JavaScript qui seront exécutées lors d'événements liés au websocket.

Les questions de l'utilisateur sont envoyées à LlmClient, comme pour les versions sans streaming. Cette fois-ci, la méthode de LlmClient retourne un TokenStream.

Le backing bean configure le TokenStream (méthode onPartialResponse, onCompleteResponse, onError) et lance le processus d'envoi des tokens (méthode start). La méthode onPartialResponse envoie le token reçu (en fait, plusieurs tokens sont souvent envoyés en une seule fois) dans le webSocket. La méthode onCompleteResponse envoie un événement particulier dans le webSocket pour déclencher l'exécution d'une fonction JavaScript qui va mettre à jour la conversation avec la réponse complète du LLM.

Pour les réponses courtes, il n'y aura pas un grand changement car les tokens sont envoyés à grande vitesse, mais si la réponse est longue, ou si le réseau est lent, vous verrez bien les tokens s'afficher au fur et à mesure.
